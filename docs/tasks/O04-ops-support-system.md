## ทำอะไร

- Ticket: คิวกลาง (รับเรื่องนี้), สร้าง, ตอบ, โอนให้, ส่งต่อทีมพัฒนา, ปิดพร้อมสาเหตุ, SLA และเปิดใหม่เมื่อลูกค้าตอบใน 7 วัน · ลูกค้าส่ง Ticket จากในแอปผ่าน API ฝั่งลูกค้า (คำขอนอก lane ถ้ายังไม่มี)
- สถานะระบบ: uptime, เวลาตอบ, error rate, คิว, การส่ง Email / LINE, Workspace ที่ใช้ทรัพยากรสูง
- เหตุขัดข้อง: เปิด, อัปเดตตามสถานะ, เผยแพร่หน้าสถานะสาธารณะ, ส่งอีเมลผู้ติดตาม
- ปิดปรับปรุง: ตั้งเวลา / เปิดทันที (อ่านอย่างเดียว · ต้องอนุมัติ) · API ฝั่งลูกค้าต้องอ่านสถานะนี้ (คำขอนอก lane)
- งานเบื้องหลังที่ล้ม: ลองใหม่ / ทิ้งพร้อมเหตุผล

**ส่งงาน 2026-11-09** · test `support-system.e2e.test.ts` 14 ข้อ (ส่วนงานที่ล้มรันเมื่อตั้ง `VALKEY_URL` แบบเดียวกับ `apps/api/test/queue.e2e.test.ts` · ในเครื่องนี้รันกับ Valkey จริงแล้วผ่านครบ) · ops-api ทั้งชุด 79 ผ่าน · `pnpm typecheck` ที่รากผ่าน

**Endpoint**
- **Ticket**:
  - `GET ops/tickets?status&assignee=me|none|<id>&workspaceId&q`: สรุปหัวหน้าจอ (เปิดอยู่, ยังไม่มีคนรับ, เกิน SLA, ตอบครั้งแรกเฉลี่ย, ความพึงพอใจ)
  - `GET ops/tickets/stats` (ผลงานรายคน 30 วัน) และ `GET ops/tickets/:id` (ข้อความ + ข้อมูลลูกค้าด้านข้าง)
  - `POST ops/tickets` (T1) และ `POST ops/tickets/:id/{claim|assign|release|escalate|solve|csat}` (T2, T3, T5)
  - `POST ops/tickets/:id/messages`: ตอบลูกค้า / บันทึกภายใน / `fromCustomer` บันทึกข้อความที่ลูกค้าส่งมาทางช่องทางอื่น
- **เข้าบัญชีเพื่อช่วยเหลือ**: `ticketId` ผูกกับ Ticket ในระบบได้ (ต้องเป็นของ Workspace นั้นและยังเปิด) · `ticketNo` แบบเดิมยังใช้ได้
- **สถานะระบบ**: `GET ops/system/status`
- **เหตุขัดข้อง**: `GET|POST ops/incidents` และ `POST ops/incidents/:id/updates` (Y3, Y4)
- **หน้าสถานะสาธารณะ** (ไม่ต้องล็อกอิน): `GET status`, `POST status/{subscribe|confirm|unsubscribe}`
- **ปิดปรับปรุง**: `GET|POST ops/maintenance` (Y5 · 202 ต้องอนุมัติ) และ `POST ops/maintenance/:id/end`
- **งานที่ล้ม**: `GET ops/jobs/failed`, `POST ops/jobs/:id/{retry|discard}` และ `POST ops/jobs/retry` (หลายรายการ)

**สิทธิ์**
- Ticket: Support / Owner (การเงินไม่เห็นข้อความใน Ticket ตาม 06 › 2)
- สถานะระบบ / ปิดปรับปรุง / งานที่ล้ม: วิศวกร (Owner ดูได้)
- เหตุขัดข้อง: วิศวกรและ Support

**คำตัดสินที่เลือกเอง**
- **SLA** ตามแพ็กเกจเป็นชั่วโมงทำการ จ.–ศ. 09:00–18:00 (ยังไม่นับวันหยุด):

  | แพ็กเกจ | ตอบครั้งแรก | แก้เสร็จ |
  |---|---|---|
  | Free | 24 | 72 |
  | Team S | 8 | 40 |
  | Team M | 4 | 24 |
  | Team L | 2 | 16 |
  | Enterprise | 1 | 8 |

  เรื่องด่วนตอบครั้งแรกภายใน 1 ชั่วโมง · ตัวเลขของ Team M / L ตรงกับหน้าจอ ส่วนแพ็กเกจอื่นตั้งเอง
- **คิวกลาง**: ยังไม่มีคนรับ = อยู่ในคิว · การแจกงานอัตโนมัติเป็นเฟส 2 · โอนได้เฉพาะเจ้าของเรื่องหรือ Owner และผู้รับต้องมีบทบาท Support
- **เปิดใหม่**: ลูกค้าตอบภายใน 7 วันหลังแก้แล้ว → เปิดใหม่ · เกินนั้น 409 ให้เปิดเรื่องใหม่ · ทุกชั่วโมงปิดถาวรเรื่องที่แก้แล้วเกิน 7 วัน (`TicketsService.closeStale`)
- **ความพึงพอใจ**: ช่วงแรกส่งอีเมลขอคะแนนให้ลูกค้าตอบกลับเป็นตัวเลข แล้วทีมกรอกผ่าน `csat`
- **ส่งต่อทีมพัฒนา (T3)**: เก็บรายละเอียดเป็นบันทึกภายใน · ยังไม่ต่อระบบบั๊กของทีมพัฒนา
- **สถานะระบบ**:
  - ตรวจ `/healthz` ของ API ทุก 30 วินาที แล้วเก็บผลในหน่วยความจำ 24 ชั่วโมง (รีสตาร์ทแล้วเริ่มใหม่) · ตั้งปลายทางด้วย env `API_HEALTH_URL`
  - error rate ของคำขอจริงยังเป็น `null` จนกว่าจะเชื่อม GlitchTip / CloudWatch
  - Workspace ที่ใช้ทรัพยากรมากสุดมาจาก `daily_usages` วันล่าสุด
  - เวอร์ชันมาจาก env `WEB_VERSION` / `API_VERSION` / `GIT_SHA`
- **งานที่ล้ม**: อ่านคิว BullMQ `jobs` ของ API ด้วย `VALKEY_URL` / `QUEUE_PREFIX` ชุดเดียวกัน (เพิ่ม dependency `bullmq` ให้ ops-api) · ไม่ตั้ง = แสดง "ยังไม่เชื่อมคิว" · ทิ้งงานแล้วเก็บชื่องาน + สาเหตุ + เหตุผลไว้ใน `staff_audit_logs`
- **ปิดปรับปรุง**:
  - ต้องอนุมัติทุกครั้ง · ช่วงที่มี Owner คนเดียว Owner ที่ขอเองอนุมัติตัวเองได้ตามกติกาเดิม
  - ไม่เกิน 24 ชั่วโมงต่อครั้ง และซ้อนกันไม่ได้
  - ปลดหรือยกเลิกได้ทันทีโดยไม่ต้องอนุมัติ · ทุกนาทีเปลี่ยนสถานะตามเวลา
  - แจ้งล่วงหน้าตอนนี้ส่งถึงผู้ติดตามหน้าสถานะตอนอนุมัติ · การเตือน 3 วัน / 1 ชั่วโมงก่อนถึงลูกค้าทุกรายยังไม่ทำ
- **หน้าสถานะสาธารณะ**: ส่ง `banner` ให้ API ลูกค้าใช้ทำแบนเนอร์ในแอป · การติดตามต้องยืนยันด้วยรหัสทางอีเมล
  - หน้าสถานะต้องอยู่ origin เดียวกับ `OPS_WEB_ORIGIN` หรือเรียกผ่าน server เพราะ AuthGuard ตรวจ Origin ของคำขอเขียน
- งานตามเวลาทั้งหมดของ ops-api ปิดได้ด้วย `OPS_JOBS=off`

**คำขอนอก lane (ยังไม่ทำ)**
1. **API ลูกค้า: ส่ง Ticket จากในแอป** · ยังไม่มี endpoint
   - สร้าง `support_tickets` และข้อความแรก พร้อม SLA ตามแพ็กเกจ (ใช้ `addBusinessHours` / `SLA_HOURS` ชุดเดียวกัน)
   - ลูกค้าตอบเรื่องเดิมต้องใช้กติกาเปิดใหม่ 7 วันเดียวกับ `TicketsService.customerReplied`
   - ให้คะแนนความพึงพอใจได้ในแอป
2. **API ลูกค้า: อ่าน `maintenance_windows` ที่ `active`**
   - `read_only`: ตอบ 503 กับคำขอเขียน
   - `import_export`: ปิดการนำเข้า / ส่งออก
   - `full`: ปิดทั้งหมด ยกเว้นทีม Friday
   - แสดงแบนเนอร์จาก `GET status`
