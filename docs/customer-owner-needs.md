# สิ่งที่เจ้าของบริษัทอยากได้จาก Friday Manage

**ร่าง 9 พ.ย. 2569** · ข้อเสนอสำหรับรุ่นถัดไป (v1.1) · UI v1.0 ล็อกแล้ว ทุกข้อในนี้จึงเป็นฟีเจอร์ใหม่ ยังไม่ได้ตัดสิน

## มุมมองที่ใช้

สมมติเป็นเจ้าของ software house ทีม 20 คน รับทำระบบให้ลูกค้าหลายรายพร้อมกัน

ตอนนี้ Friday Manage ตอบได้ดีว่า **"งานไปถึงไหน ใครงานล้น อะไรเสี่ยงจะช้า"** แต่ยังตอบคำถามที่เจ้าของบริษัทถามทุกเดือนไม่ได้:

1. โปรเจกต์นี้ได้กำไรหรือขาดทุน
2. เสนอราคาครั้งหน้าควรประเมินกี่ Man-Day
3. รับงานใหม่ได้ไหม หรือต้องจ้างคนเพิ่ม
4. เงินที่ควรได้หายไปตรงไหน

## ข้อมูลที่มีอยู่แล้วในระบบ

ระบบเก็บข้อมูลหลายอย่างไว้แล้ว แต่ยังไม่มีหน้าไหนเอามาประกอบกัน

| ข้อมูล | อยู่ที่ |
|---|---|
| งบประมาณโปรเจกต์ | `project.budget_satang` (ช่อง "ติดตามงบประมาณ" ตอนสร้างโปรเจกต์) |
| อัตราค่าแรง | `project.hourly_rate_satang` (ค่าเดียวทั้งโปรเจกต์) |
| เวลาที่ใช้จริง | `time_log` (เปิดเป็นรายโปรเจกต์ · ค่าเริ่มต้นปิด) |
| ประมาณการ | Size / Man-Day ของงานและ Sub-task |
| วันเริ่ม / จบจริง | `actual_start`, `actual_end` บันทึกเองเมื่อสถานะเปลี่ยน |
| แผนตั้งต้นและการแก้แผน | `plan_baseline`, `baseline_item`, `plan_change` |
| เวลาของแต่ละคน | `workspace_member.capacity_hours_week` และที่แบ่งให้แต่ละโปรเจกต์ |
| ลูกค้าของโปรเจกต์ | `project.client_name` · ลูกค้าเข้ามาดูเป็น Guest ได้ |

## สิ่งที่อยากได้ เรียงตามความสำคัญ

### 1. กำไรต่อโปรเจกต์ · สำคัญที่สุด

**อยากรู้:** มูลค่าสัญญาเทียบกับต้นทุนจริงถึงวันนี้ และคาดว่าจบแล้วจะเหลือกำไรเท่าไร

- ต้นทุนจริง = Man-Day ที่ใช้จริงของแต่ละคน × ต้นทุนต่อวันของคนนั้น
- คาดการณ์ตอนจบ = ต้นทุนถึงวันนี้ + Man-Day ที่เหลือ × ต้นทุนเฉลี่ย
- เตือนเมื่อใช้งบเกิน 80% แต่งานยังไม่ถึง 80%

**ต้องเพิ่ม:**
- มูลค่าสัญญา (ราคาขาย) แยกจากงบต้นทุน
- ต้นทุนต่อคน หรือต่อระดับ (Junior / Mid / Senior) เพราะอัตราเดียวทั้งโปรเจกต์คิดกำไรไม่ได้
- สิทธิ์ใหม่: เฉพาะ Owner และฝ่ายการเงินเห็นตัวเงิน (ข้อมูลเงินเดือนอ่อนไหว)
- ทางเลือกเมื่อทีมไม่บันทึกเวลา: ใช้ Man-Day ของงานที่ปิดแล้วแทน และระบุว่าเป็นค่าประมาณ

### 2. ประเมินแม่นแค่ไหน

**อยากรู้:** Man-Day ที่ประเมินเทียบกับที่ใช้จริง เพื่อเสนอราคาครั้งหน้าให้แม่นขึ้น

- แยกตาม Module, ประเภทงาน (Task / Bug / Story), ขนาด (XS–XL) และคน
- เช่น "งานขนาด M ของทีม Backend ใช้จริงเฉลี่ย 1.4 เท่าของที่ประเมิน"
- ใช้ตอนสร้างโปรเจกต์ใหม่: แนะนำตัวคูณจากโปรเจกต์ที่คล้ายกัน

**ต้องเพิ่ม:** หน้ารายงานอย่างเดียว ข้อมูลมีเกือบครบแล้ว (ประมาณการ + `time_log` หรือ `actual_start` / `actual_end`)

### 3. งานที่เพิ่มนอกสัญญา (scope creep)

**อยากรู้:** ลูกค้าขอเพิ่มอะไรหลังเซ็นสัญญา และเก็บเงินเพิ่มได้เท่าไร

- แยกงานที่อยู่ในขอบเขตตอนตั้ง Baseline ออกจากงานที่เพิ่มทีหลัง
- รวมงานที่เพิ่มเป็น "ใบขอเปลี่ยนแปลง" (Change Request) พร้อม Man-Day และราคา ส่งให้ลูกค้าอนุมัติ
- รายงานว่าโปรเจกต์นี้โตจากขอบเขตเดิมกี่ % และเก็บเงินเพิ่มได้กี่ %

**ต้องเพิ่ม:** ป้าย "นอกขอบเขต" บนงาน และ entity ใบขอเปลี่ยนแปลง · ต่อยอดจาก `plan_baseline` และ `plan_change` ที่มีอยู่

### 4. คนว่างกับงานที่กำลังเข้า

**อยากรู้:** เดือนหน้าใครว่าง และถ้ารับโปรเจกต์ที่กำลังจะเซ็น ทีมพอหรือไม่

- อัตราการใช้คน: ชั่วโมงที่เก็บเงินลูกค้าได้ ÷ ชั่วโมงทำงานทั้งหมด ต่อคนและทั้งบริษัท
- โปรเจกต์สถานะ "กำลังจะเซ็น" ที่จองคนไว้ล่วงหน้าแบบไม่ยืนยัน
- มุมมองรายเดือน 3–6 เดือนข้างหน้า แยกตามทักษะ (Frontend / Backend / QA / Design)

**ต้องเพิ่ม:** ทักษะของคน, สถานะโปรเจกต์แบบยังไม่ยืนยัน, งานที่ไม่เก็บเงินลูกค้า (งานภายใน, presales)

### 5. งวดเงินผูกกับ Milestone

**อยากรู้:** Milestone ไหนเสร็จแล้วแต่ยังไม่ได้วางบิล

- ผูก Milestone กับงวดเงินและ % ของสัญญา
- ลูกค้ากดรับงาน (UAT sign-off) ผ่านหน้า Guest แล้วแจ้งฝ่ายบัญชีทาง LINE / อีเมล
- รายการงวดที่ถึงกำหนดแต่ยังไม่วางบิล

### 6. คุณภาพหลังส่งมอบ

**อยากรู้:** ระบบที่ส่งไปแล้วมีบั๊กเท่าไร และต้นทุนช่วงรับประกันสูงแค่ไหน

- บั๊กที่เจอใน UAT และหลังขึ้นระบบจริง แยกตาม Module
- อัตรางานที่ต้องเปิดใหม่ (reopen) ต่อคนและต่อ Module
- Man-Day ที่ใช้แก้บั๊กหลังส่งมอบ (ต้นทุนรับประกัน)

**ต้องเพิ่ม:** ช่อง "พบในช่วง" ของบั๊ก (dev · UAT · production)

### 7. สัญญาดูแลระบบ (MA)

**อยากรู้:** ลูกค้าใช้ชั่วโมง MA ไปเท่าไรแล้ว และตอบปัญหาทันตาม SLA หรือไม่

- ชั่วโมงที่สัญญาให้ต่อเดือน / ต่อปี เทียบกับที่ใช้จริง
- งานแจ้งปัญหาหลังขึ้นระบบจริง: ระดับความรุนแรง, เวลาตอบ, เวลาแก้
- เตือนเมื่อใช้ชั่วโมงเกินสัญญา เพื่อเรียกเก็บส่วนเกิน

### 8. หน้ารวมสำหรับเจ้าของ

ทุกโปรเจกต์ในหน้าเดียว: สถานะ, ความเสี่ยง, % งบที่ใช้, กำไรที่คาด, งวดเงินที่รอวางบิล และคนว่างเดือนหน้า

## ลำดับที่แนะนำ

| ลำดับ | เรื่อง | เหตุผล |

| 1 | ข้อ 2 ประเมินแม่นแค่ไหน | ใช้ข้อมูลที่มีอยู่แล้ว ทำได้เร็วที่สุด |
| 2 | ข้อ 1 กำไรต่อโปรเจกต์ | ตอบคำถามหลักของเจ้าของบริษัท และเป็นเหตุผลที่ยอมจ่ายแพ็กเกจแพงขึ้น |

## ผลต่อธุรกิจของ Friday Manage

- ข้อ 1–3 และข้อ 8 เหมาะเป็นฟีเจอร์ของแพ็กเกจระดับสูง (Team L / Enterprise) หรือ add-on "การเงินโปรเจกต์"
- การเปิดบันทึกเวลาเป็นค่าเริ่มต้นจะทำให้ข้อ 1–2 แม่นขึ้น แต่ทีม Dev มักไม่ชอบ จึงควรให้บันทึกเร็ว เช่น ใส่ Man-Day ตอนปิดงาน
- ใช้ `cancellation_feedback` และ `feature.used` ใน [05-business-metrics](spec/05-business-metrics.md) วัดว่าลูกค้าขาดฟีเจอร์เหล่านี้จริงหรือไม่ ก่อนลงทุนสร้าง

## คำถามที่รอตัดสิน

1. ทำเรื่องการเงินโปรเจกต์ในแพ็กเกจปกติ หรือขายแยกเป็น add-on
2. ต้นทุนต่อคน: ให้กรอกรายคน หรือรายระดับเท่านั้น (รายระดับไม่เปิดเผยเงินเดือนของแต่ละคน)
3. ใบขอเปลี่ยนแปลง (Change Request) ต้องให้ลูกค้าอนุมัติในระบบด้วยหรือไม่
